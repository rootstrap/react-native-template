Managing environment variables in your project is an essential task, but it can also be challenging. That's why we have included a complete setup for environment variables in this project. This setup comes with validation and type-checking using the `zod` library.

All the code related to environment variables is located in the `env.js`, `env-fields.js` and `src/lib/env.js` files. The `env.js` read the `APP_ENV` variable and loads the correct `.env` file, then defines the schemas of the environment variables for client and build-time using the `envField` helpers from `env-fields.js` (built on top of `zod`), reads the declared variables from `process.env`, and returns the parsed object, or throws errors in case of invalid or missing variables.

To increase security, we are splitting environment variables into two parts:

- **Client Variables**: Variables that are safe to be exposed to the client and used in your `src` folder. These variables are passed to the client side using the `extra` configuration in the `app.config.ts` file.
- **Build Time Variables**: Variables that we don't need on the client-side and are only used in the `app.config.ts`, for example `SENTRY_AUTH` to upload the source maps to Sentry.

By using this pre-configured setup for environment variables, you can focus on building your project without worrying about managing and validating your environment variables.

This setup is highly inspired by [T3 Stack](https://create.t3.gg/) 👌

## Adding a new environment variable to the project.

To add a new environment variable to the project, follow these steps:

1. Add the new environment variable to the correct schema inside the `env.js` file based on this simple rule :
   If the variable is used in the `src` folder, add it to the `client` schema, otherwise add it to the `buildTime` schema.

   Declare it with one of the `envField` builders (`envField.string()`, `envField.number()`, `envField.boolean()` or `envField.enum([...])`). The value is read from `process.env` automatically and converted to the declared type, so this is the only place where you need to declare the variable.

   Every variable without a static value (see `clientStaticValues` and `buildTimeStaticValues`) is read from `process.env`, so it must be declared with an `envField` builder. Declaring it with any other schema (e.g. a plain `zod` schema such as `z.number()`) throws an error naming the variable, because its raw value would always be a string.

This will ensure that the new variable is validated correctly. and make sure we are only sending the correct vars to the client side
Here's an example:

```js title="env.js"
const clientEnvSchema = envSchema({
  // ...
  // add the new environment variable here/ accessible on the client side and build time(app.config.ts)
  NEW_ENV_VAR: envField.string(),
  NEW_NUMBER_VAR: envField.number({ default: 4321 }),
  NEW_FLAG_VAR: envField.boolean({ optional: true }),
  NEW_MODE_VAR: envField.enum(['light', 'dark'], { default: 'light' }),
});

const buildTimeEnvSchema = envSchema({
  // ...
  // add the new environment variable here / accessible only on build time(app.config.ts)
  NEW_SECRET_ENV: envField.string(),
});
```

2. Pick the right options for the variable. Every `envField` builder accepts the following options:

| Option     | Description                                                                          |
| ---------- | ------------------------------------------------------------------------------------ |
| `optional` | When `true`, the variable can be missing or empty and its value will be `undefined`. |
| `default`  | Value used when the variable is missing or empty.                                    |

Without options, the variable is required. Empty values (e.g. `API_URL=`) are treated as missing. Use the schema returned by `envField` as is and pass these options instead of chaining `zod` methods on it (e.g. `envField.string().optional()` or `.describe()`): a chained schema isn't recognized as an env field, so loading `env.js` throws. Values are converted as follows:

- `envField.string()`: the value is used as is.
- `envField.number()`: only plain decimal numbers (e.g. `42` or `-3.5`) are accepted; any other value (e.g. `abc`, `Infinity`, `0x10` or `1e3`) is rejected.
- `envField.boolean()`: only `true` and `false` are accepted, case-insensitively (e.g. `TRUE` or `False`); any other value (e.g. `1` or `yes`) is rejected.
- `envField.enum(values)`: only one of the given values is accepted (e.g. `APP_ENV` must be `development`, `production`, `qa` or `staging`).

Invalid values are reported with the accepted format and the received value, for example `VAR_BOOL=yes` is reported as `must be 'true' or 'false', received "yes"`.

:::caution[Upgrading from a previous version of the template]
Number and boolean variables used to be converted manually in `env.js` with a looser conversion: any boolean value other than `true` (such as `1` or `yes`) silently became `false`, and numbers such as `1e3`, `0x10` or values with surrounding spaces were accepted. The `envField` builders are stricter, so those values now fail validation instead. If you pull template updates (for example, through the `sync-with-upstream.yml` workflow), review your `.env` files and the env files used by your CI and EAS builds, and make sure number variables are plain decimal numbers and boolean variables are `true` or `false`.
:::

3. Add the new environment variable to your `.env` files. Make sure to include it in all relevant files (`development`, `staging`, and `production`). Here's an example:

```bash title=".env.{APP_ENV}"
# ...
# add the new environment variable here
NEW_ENV_VAR=my-new-var
```

:::note
if you are not pushing env files to your repo(recomended), please make sure to check the [App releasing process](/ci-cd/app-releasing-process/#github-action-and-env-variables) to see how to create the env file on the fly before the prebuild script in the github actions.
:::

4. Make sure to run `pnpm prebuild` to load the new values.

```bash
pnpm prebuild
```

5. The new environment variable is now ready to use in your project. You can access it in your code using the `Env` object, like this:

```ts title="client.ts"
import { Env } from '@env';
import axios from 'axios';
export const client = axios.create({
  baseURL: Env.API_URL,
});
```

:::note[Important]
Using `import { Env } from '@env';` will import the env from the `src/lib/env.js` file, which export client only env vars.
:::

6. Use `APP_ENV` to load the correct `.env` file :

```bash
APP_ENV=production pnpm start -cc
```

As mentioned earlier, `zod` is used to validate environment variables at runtime and build time. If there are any missing or invalid variables, you'll see an error message with information on what needs to be fixed. Here's an example error message:

```bash
❌ Invalid environment variables: { TEST: [ 'Required' ] }
❌ Missing or invalid variables in .env.development file. Make sure all required variables are defined with valid values in the .env.development file.
💡 Tip: If you recently updated the .env.development file and the error still persists, try restarting the server with the -c flag to clear the cache.
```

:::note[When validation runs]
`env.js` decides whether to validate from the `package.json` script being run (`npm_lifecycle_script`). The variables are only validated when that script runs the app (`expo start` or `expo run`, e.g. `pnpm start` or `pnpm ios`), or when it builds the app with one of the commands listed in `ENVIRONMENT_DEPENDANT_SCRIPTS` (such as `eas build` or `expo export`) and the build runs on EAS or the script includes `--local`, `eas-cli-local-build-plugin` or `expo export`. Only these flows fail fast on missing or invalid variables. Validation is skipped for any other case, such as a local `pnpm prebuild:<env>` (`expo prebuild` outside EAS), `eas update`, or commands run directly instead of through a `package.json` script (e.g. `npx expo start`): missing or invalid values end up as `undefined` in `Env` and `ClientEnv`, and therefore in the `extra` field of the app config, without any error.
:::

:::note[Important]
As `dotenv` handles variables as strings, the `envField` builders convert them to the declared type (`string`, `number` or `boolean`) before validating them, so you don't need to parse them yourself.
:::

## How it works

#### ✅ Validate and parse environment variables

If you take a look at the `env.js` file, you will notice that the file is split into three main parts as shown below:

<Code file="env.js" />

**In the first part** We load the correct `.env` file based on the `APP_ENV` variable using `dotenv` package. If the `APP_ENV` variable is not defined, we default to `development`.

we define some static variables for the app such as the app name, bundle Id and package. While these variables can be added to the `.env` files, we recommend keeping them in the `env.js` file as they are not meant to change. To handle different app variants, you can add suffixes to these variables using the `withEnvSuffix` function. The bundle Id, package and app scheme are already suffixed this way: on `production` they keep their base value, and on the other environments they end with `.<APP_ENV>` (for example, the `staging` scheme is `RootstrapApp.staging`). See [App scheme and deep links](/guides/navigation/#app-scheme-and-deep-links) for how to build links for each environment.

**In the second part**, we define the schemas of the environment variables with `envSchema`. Every variable is declared with the `envField` builders: variables loaded from the `.env` file and static values defined in `env.js` (such as `NAME` or `BUNDLE_ID`), whose values are set in the `clientStaticValues` and `buildTimeStaticValues` objects.

We split the environment variables into two parts:

- **Client Variables**: Variables that are safe to be exposed to the client and used in the `src` folder.

- **Build Time Variables**: Variables that we don't need on the client-side and are only used in the `app.config.ts`, for example, `SENTRY_AUTH` to upload the source maps to Sentry.

These schemas are used to validate the environment variables. All the environment variables should be added to the correct schema.

The values of the variables declared in each schema are read from `process.env` automatically, so each variable is declared only once. We use the `InferEnv` type from `env-fields.js` to infer the environment variables' types from the schema, so `Env` and `ClientEnv` are typed with the converted values (for example, `number` for `envField.number()`).

**Finally**, in the third part, we merge variables to `_wholeEnv`, parse it using the zod schema, and return the parsed object as well as the client environment variable, or throw errors in case of invalid or missing variables.
