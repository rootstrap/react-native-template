The template comes with over 10 GitHub Actions workflows that help you automate the process of checking, testing, releasing, and much more.

All those workflows are self-documented and contain all details directly inside the workflow file as comments. This approach makes it easier to understand what each workflow does and how to use it without having to go back and forth between the documentation and the workflow file.

This page lists all workflows and actions we use and adds more details on the approach we are using to make those workflows as simple as possible.

All files related to GitHub Actions are located in the `.github/workflows` and `.github/actions` folders.

## Actions

You can think of actions as functions that are used by workflows to perform a specific task and allow you to reuse the same task in multiple workflows without duplicating the code which made them easier to maintain.

### ⚙️ Sync with template

This workflow keeps a project created from the template up to date: it computes the diff between the template release used by the project (`rsMetadata.templateVersion` in `package.json`) and the template release to sync with, applies it to the project, and opens a Pull Request with the changes.

Some template files and folders only make sense in the template repository (the CLI, the documentation site, template-only workflows, etc.) and must never be carried into the project. These paths are listed in the `.appignore` file at the root of the template repository:

- One path (file or folder) per line, relative to the repository root.
- Lines starting with `#` and blank lines are ignored. Inline comments are not supported.
- If the file is missing or has no paths, the workflow falls back to a default list and logs a warning.

The workflow reads `.appignore` from the template release it syncs with, so any change in the listed paths is excluded from the update Pull Request. To stop syncing a new template path into projects, add it to `.appignore` in the template repository; projects running a version of the workflow that reads `.appignore` pick it up with the next template release, without changing their workflow. Template releases published before `.appignore` was introduced fall back to a default list defined in the workflow.

:::note
In generated projects this workflow lives in `.github/workflows/sync-with-template.yml`, while the template keeps it in `.github/project-workflows/sync-with-template.yml`, so template updates to the workflow itself are not applied automatically. Projects created before `.appignore` was introduced still run a workflow with a hard-coded `DIFF_EXCLUDED_ROUTES` list: replace their `.github/workflows/sync-with-template.yml` with the latest version from the template once to start using `.appignore`. Until then, a template sync may add the `.appignore` file to the project; it is not used by the project and can be deleted.
:::
